# 产品需求文档 - 旅行规划 Agent

## 1. 产品概述

### 1.1 需求背景与目标

个人旅行规划流程繁琐：需要在多个平台比价、查天气、排行程、逐一预订。本产品通过大模型 Agent 将"模糊出行意愿"一站式转化为"可执行的预订清单"，大幅降低规划成本。

**核心目标**：
- 将旅行规划时间从数小时压缩到 10 分钟内
- 从模糊需求到可预订链接，全程对话式完成
- Agent 不触碰支付，仅提供决策辅助和跳转引导

### 1.2 用户画像

| 属性 | 描述 |
|------|------|
| 角色 | 产品所有者本人（单人使用，无多用户场景） |
| 技术背景 | 开发者，熟悉命令行和 API |
| 使用频率 | 每月 1-3 次旅行规划 |
| 核心诉求 | 快速获得高性价比方案，减少跨平台比价时间 |
| 使用终端 | Web 网页端 / 小程序端（优先 Web） |

### 1.3 核心价值

- **省时**：对话式交互替代多平台手动搜索
- **智能推荐**：基于预算、时间、偏好综合推荐目的地
- **端到端**：从灵感到预订链接一条龙，不断链

## 2. 用户故事

| 编号 | 角色 | 行为 | 价值 |
|------|------|------|------|
| US-01 | 用户 | 输入模糊出行需求（时间、预算、偏好） | 快速获得匹配的目的地推荐 |
| US-02 | 用户 | 查看目的地推荐卡片（天气/交通/费用） | 做出有依据的目的地选择 |
| US-03 | 用户 | 选定目的地后获取完整行程表 | 无需自己排列组合行程 |
| US-04 | 用户 | 对行程提出修改意见 | 行程符合个人节奏偏好 |
| US-05 | 用户 | 确认行程后逐项获取预订链接 | 按顺序完成所有预订，不遗漏 |
| US-06 | 用户 | 支付完成后通知 Agent 进入下一项 | 有序推进，状态可追踪 |

## 3. 核心功能详细描述

### 3.1 功能：目的地探索与推荐 [P0]

- **功能概述**：根据用户模糊需求，推荐 2-3 个目的地方案
- **触发入口**：用户发送第一条消息描述出行需求
- **输入**：
  - 出行时间范围（必填，可模糊如"清明前后"）
  - 预算范围（必填，如"4000以内"）
  - 偏好标签（选填，如"海边""温暖""人少"）
  - 出发城市（必填，首次使用时设定默认值）
- **输出**：2-3 个目的地推荐卡片，每张包含：
  - 目的地名称 + 一句话推荐理由
  - 当期天气概况（气温范围、降水概率）
  - 交通方式及预估耗时/费用（飞机/高铁）
  - 酒店均价范围（经济型/舒适型）
  - 总费用预估区间
  - 票务示例（最近一班高铁/航班的时间和价格）
- **操作流程**：
  1. 用户输入自然语言需求
  2. Agent 解析意图，提取结构化参数（时间/预算/偏好/出发地）
  3. 若关键参数缺失，Agent 追问补全
  4. Agent 调用天气 API + 票务 API + 酒店 API 获取实时数据
  5. 大模型综合数据生成推荐卡片
  6. 返回 2-3 个方案供用户选择
- **异常处理**：
  - API 超时/失败：使用缓存数据或大模型经验估算，标注"预估数据，仅供参考"
  - 无匹配目的地：提示用户放宽条件（预算/时间/偏好）
  - 参数解析失败：Agent 用引导式提问重新收集

**验收标准**：
- [ ] Given 用户输入"五一假期，预算5000，想去海边"，When Agent 处理完成，Then 返回 2-3 个沿海城市推荐，每个包含天气/交通/费用信息
- [ ] Given 外部 API 全部失败，When Agent 降级处理，Then 仍返回基于大模型知识的推荐，并标注数据为预估
- [ ] Given 用户未提供出发城市，When Agent 检测到缺失，Then 主动追问出发地

### 3.2 功能：行程详细规划 [P0]

- **功能概述**：用户选定目的地后，生成完整的日程行程表
- **触发入口**：用户回复选择某个目的地（如"选第2个"或"去三亚"）
- **输入**：用户选定的目的地 + 前序收集的时间/预算/偏好
- **输出**：结构化行程表，包含：
  - 去程交通（具体班次、时间、价格）
  - 住宿推荐（酒店名称、价格、位置）
  - 每日行程安排（景点/活动、时间段、交通方式、门票费用）
  - 返程交通（具体班次、时间、价格）
  - 总费用明细表（分类汇总 + 总计）
- **操作流程**：
  1. Agent 确认用户选择
  2. 调用票务 API 查询具体班次
  3. 调用酒店 API 查询可用房源
  4. 大模型编排每日行程（考虑地理位置、开放时间、体力分配）
  5. 汇总费用，生成行程表
  6. 询问用户是否需要调整
- **数据约束**：
  - 费用精度：元，保留整数
  - 时间格式：YYYY-MM-DD HH:mm
  - 每日行程不超过 3 个主要景点
  - 总费用不超过用户预算（允许 10% 浮动并提示）
- **异常处理**：
  - 票务售罄：推荐相邻时间班次
  - 酒店无房：推荐同区域替代酒店
  - 超预算：标注超出金额，建议降级方案

**验收标准**：
- [ ] Given 用户选定三亚，When 行程生成完成，Then 包含去程/住宿/每日安排/返程/费用汇总五部分
- [ ] Given 生成的行程总费用超预算 15%，When 展示给用户，Then 明确标注超出金额并提供降级建议
- [ ] Given 用户要求"把第二天的景点换掉"，When Agent 处理，Then 仅修改第二天内容，其余不变

### 3.3 功能：行程确认与预订引导 [P0]

- **功能概述**：用户确认行程后，Agent 按顺序为每项服务生成预订链接，用户逐项完成支付
- **触发入口**：用户回复"确认行程"或类似肯定表达
- **输入**：已确认的完整行程表
- **输出**：按预订顺序逐项输出：
  - 服务名称（如"去程高铁 G1234"）
  - 预订平台（携程 > 飞猪 > 去哪儿，按优先级）
  - 预填搜索链接 / 深度链接（含日期、车次/航班号、人数等参数）
  - 预估价格
  - 备选平台链接（如首选平台无货）
- **预订顺序**：
  1. 去程交通（最易售罄，优先锁定）
  2. 住宿
  3. 返程交通
  4. 景点门票（如需预约）
- **操作流程**：
  1. Agent 输出第一项预订信息和链接
  2. 用户点击链接跳转平台完成支付
  3. 用户回复"已订"或"搞定"
  4. Agent 记录状态，输出下一项
  5. 若用户回复"跳过"，标记该项为未预订，继续下一项
  6. 全部完成后，输出预订汇总清单（已订/未订/总花费）
- **数据约束**：
  - 链接必须为 HTTPS
  - 链接参数需 URL 编码
  - Agent 绝不收集或存储支付信息
- **异常处理**：
  - 平台链接失效：提供备选平台链接
  - 用户长时间未回复：不主动催促，保持状态等待
  - 用户中途取消：保存当前进度，下次可继续

**验收标准**：
- [ ] Given 用户确认行程，When Agent 开始预订引导，Then 按"去程-住宿-返程-门票"顺序逐项输出
- [ ] Given 用户回复"已订"，When Agent 处理，Then 标记当前项为已完成并输出下一项
- [ ] Given 用户回复"跳过"，When Agent 处理，Then 标记为未预订并继续下一项
- [ ] Given 全部项目处理完毕，When Agent 汇总，Then 输出完整预订状态清单和实际总花费

### 3.4 功能：行程修改与调整 [P1]

- **功能概述**：在行程规划阶段，用户可对生成的行程提出局部修改
- **触发入口**：用户在行程展示后提出修改意见
- **支持的修改类型**：
  - 更换某天的景点
  - 调整出发/返回时间
  - 更换酒店档次
  - 增减行程天数
- **约束**：修改后自动重新计算费用汇总

**验收标准**：
- [ ] Given 用户要求更换酒店为五星级，When Agent 调整，Then 更新住宿信息和总费用
- [ ] Given 用户要求多玩一天，When Agent 调整，Then 新增一天行程并更新返程和费用

### 3.5 功能：历史行程存储与恢复 [P2]

- **功能概述**：本地存储历史规划记录，支持查看和恢复中断的规划
- **存储内容**：用户需求、推荐结果、最终行程、预订状态
- **存储方式**：本地 SQLite 或 JSON 文件

**验收标准**：
- [ ] Given 用户中断规划后重新启动，When 输入"继续上次"，Then 恢复到中断时的状态

### 4.1 主流程（文字描述）

```
用户启动 Agent
    |
    v

    |

    |是
    v
Agent 调用 API 获取数据
    |
    v
Agent 返回 2-3 个目的地推荐卡片
    |
    v
用户选择目的地（或要求重新推荐）
    |
    v
Agent 生成完整行程表
    |
    v
[用户满意?] --否--> 用户提出修改 --> Agent 局部调整 --> 回到展示
    |是
    v
用户确认行程
    |
    v
Agent 输出第1项预订链接
    |
    v
用户完成支付，回复"已订" / "跳过"
    |
    v
[还有下一项?] --是--> Agent 输出下一项预订链接 --> 回到用户支付
    |否
    v
Agent 输出预订汇总清单
    |
    v
流程结束，行程存档
```

### 4.2 状态机

```
[IDLE] --> 收到用户需求 --> [COLLECTING_PARAMS]
[COLLECTING_PARAMS] --> 参数完整 --> [RECOMMENDING]
[RECOMMENDING] --> 推荐完成 --> [AWAITING_SELECTION]
[AWAITING_SELECTION] --> 用户选择 --> [PLANNING]
[AWAITING_SELECTION] --> 用户要求重新推荐 --> [RECOMMENDING]
[PLANNING] --> 行程生成 --> [AWAITING_CONFIRMATION]
[AWAITING_CONFIRMATION] --> 用户要求修改 --> [PLANNING]
[AWAITING_CONFIRMATION] --> 用户确认 --> [BOOKING]
[BOOKING] --> 输出链接 --> [AWAITING_BOOKING_FEEDBACK]
[AWAITING_BOOKING_FEEDBACK] --> 用户确认/跳过 --> [BOOKING] (下一项)
[AWAITING_BOOKING_FEEDBACK] --> 全部完成 --> [COMPLETED]
[COMPLETED] --> 存档 --> [IDLE]
```

**状态持久化**：每次状态变更时写入本地存储，支持断点恢复。

## 5. 信息架构

### 5.1 核心数据模型

```
TravelSession {
  id: string (UUID)
  created_at: datetime
  updated_at: datetime
  state: enum (IDLE | COLLECTING_PARAMS | RECOMMENDING | AWAITING_SELECTION | PLANNING | AWAITING_CONFIRMATION | BOOKING | COMPLETED)
  
  user_request: {
    raw_input: string          // 用户原始输入
    departure_city: string     // 出发城市
    travel_dates: {start: date, end: date}  // 出行日期范围
    budget: int                // 预算（元）
    preferences: string[]      // 偏好标签
  }
  
  recommendations: [           // 推荐列表
    {
      destination: string
      reason: string
      weather: {temp_range: string, rain_prob: float}
      transport: {mode: string, duration: string, price: int}
      hotel_range: {economy: int, comfort: int}
      total_estimate: {min: int, max: int}
      sample_tickets: [{type: string, number: string, time: string, price: int}]
    }
  ]
  
  itinerary: {                 // 确认的行程
    destination: string
    outbound: {type: string, number: string, datetime: string, price: int}
    hotel: {name: string, price_per_night: int, nights: int, location: string}
    daily_plans: [
      {
        date: date
        activities: [{time: string, name: string, transport: string, cost: int}]
      }
    ]
    return: {type: string, number: string, datetime: string, price: int}
    total_cost: int
  }
  
  booking_progress: [          // 预订进度
    {
      item_type: enum (OUTBOUND | HOTEL | RETURN | TICKET)
      item_name: string
      platform: string
      link: string
      status: enum (PENDING | BOOKED | SKIPPED)
      actual_cost: int?
    }
  ]
}
```

### 5.2 本地存储方案

- **存储引擎**：SQLite（单文件，零配置）
- **表结构**：
  - `sessions`：存储 TravelSession JSON（以 id 为主键）
  - `config`：存储用户默认配置（出发城市等）
- **文件位置**：`~/.travel-agent/data.db`

## 6. 接口依赖清单

| 序号 | API 名称 | 用途 | 优先级 | 降级策略 |
|------|----------|------|--------|----------|
| 1 | 豆包大模型 (Doubao) | 意图解析、行程编排、对话生成 | 核心 | 无降级，服务不可用则提示用户稍后重试 |
| 2 | 聚合数据-火车票 API | 查询高铁/火车班次和票价 | 高 | 降级为大模型经验估算，标注"预估" |
| 3 | Amadeus Flight API | 查询航班信息和票价 | 高 | 降级为大模型经验估算，标注"预估" |
| 4 | 携程开放平台 | 酒店查询、深度链接生成 | 高 | 降级为飞猪 -> 去哪儿 |
| 5 | 飞猪开放平台 | 酒店/机票备选查询 | 中 | 降级为去哪儿或通用搜索链接 |
| 6 | 天气 API（和风天气/OpenWeather） | 目的地天气查询 | 中 | 降级为大模型历史气候知识 |
| 7 | 去哪儿 | 最终备选预订平台 | 低 | 生成通用搜索引擎链接 |

**降级原则**：
- 每个 API 调用设置 5 秒超时
- 失败后重试 1 次（间隔 2 秒）
- 二次失败触发降级
- 降级数据必须在输出中明确标注

## 7. 非功能需求

### 7.1 性能

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 单轮响应时间 | < 15 秒 | 包含 API 调用和大模型推理 |
| 推荐生成时间 | < 20 秒 | 需并行调用多个 API |
| 行程生成时间 | < 15 秒 | 含票务和酒店查询 |
| 本地存储读写 | < 100ms | SQLite 本地操作 |

### 7.2 安全

- API Key 存储在环境变量中，不硬编码
- Agent 绝不接触用户支付信息
- 生成的链接仅为搜索/预填链接，不含敏感数据
- 本地存储不加密（单人使用，物理安全由用户保障）

### 7.3 可靠性

- API 调用：超时 5s + 重试 1 次 + 降级
- 会话状态：每次状态变更持久化，支持断点恢复
- 错误处理：所有异常捕获后给出用户友好提示，不暴露技术细节

### 7.4 可维护性

- 模块解耦：推荐模块、规划模块、预订模块独立
- API 适配器模式：每个外部 API 封装为独立适配器，便于替换
- 配置外置：API 端点、超时时间、重试次数等可配置

## 9. 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 第三方 API 不稳定或限流 | 推荐/规划数据不准确 | 高 | 多源降级 + 大模型兜底 + 缓存热门路线 |
| 携程/飞猪深度链接规则变更 | 预订链接失效 | 中 | 适配器模式隔离变更；备选方案为通用搜索链接 |
| 大模型幻觉（虚构航班/酒店） | 用户信任度下降 | 中 | API 数据优先；大模型生成内容标注数据来源 |
| 票价实时波动 | 实际价格与预估不符 | 高 | 明确标注"预估价格，以实际为准"；预订时展示实时价 |
| 豆包大模型服务中断 | 整个 Agent 不可用 | 低 | 提示用户稍后重试；考虑备用模型（如通义千问） |
| 单人项目维护成本 | API 变更后无人及时修复 | 中 | 模块化设计降低修改范围；关键 API 加监控告警 |

## 10. 术语表

| 术语 | 定义 |
|------|------|
| Agent | 基于大模型的对话式智能助手 |
| 深度链接 (Deep Link) | 直接跳转到 App/网站特定页面的链接，可预填参数 |
| 降级 | API 不可用时使用备选数据源或估算值 |
| 会话 (Session) | 一次完整的旅行规划过程，从需求输入到预订完成 |
| 预填链接 | URL 中携带搜索参数（日期、目的地等），打开后自动填入搜索条件 |

## 11. 前端交互原型

### 11.1 界面架构

采用对话式 UI + 结构化卡片混合布局，移动端优先（375px），兼容桌面端。

**5 个核心视图**：

| 视图 | 对应状态 | 核心元素 |
|------|----------|----------|
| 对话界面 | IDLE / COLLECTING_PARAMS | 聊天气泡、输入框、状态栏 |
| 目的地推荐 | RECOMMENDING / AWAITING_SELECTION | 2-3 张推荐卡片、选择按钮 |
| 行程表 | PLANNING / AWAITING_CONFIRMATION | 时间线、交通/酒店/日程卡片、费用汇总 |
| 预订引导 | BOOKING / AWAITING_BOOKING_FEEDBACK | 进度条、预订项列表、操作按钮 |
| 预订完成 | COMPLETED | 状态汇总、总花费、完成按钮 |

### 11.2 设计规范

- **主色调**：蓝青色系（#2196F3 / #00BCD4）
- **卡片样式**：圆角 12px、轻阴影、白底
- **字体**：系统默认字体栈（-apple-system, sans-serif）
- **间距**：8px 基础网格
- **响应式**：max-width 420px 居中，桌面端自适应

### 11.3 交互说明

1. **对话界面**：用户输入需求后，Agent 消息以气泡形式逐条展示，顶部状态栏实时更新当前阶段
2. **推荐卡片**：嵌入对话流中，点击"选择这个"触发行程生成
3. **行程表**：时间线纵向排列，底部双按钮（确认/修改）
4. **预订引导**：当前项高亮，已完成项绿色勾选，逐项推进
5. **完成页**：汇总所有预订状态和实际花费
