# 旅游助手Agent 产品需求文档

**版本**：1.0  
**作者**：个人开发者  
**日期**：2026-05-17  
**状态**：初始草案

---

## 1. 项目背景与目标

### 1.1 背景
个人旅行规划往往需要在多个平台反复搜索机票、火车票、酒店和攻略，流程繁琐。现有AI助手多只停留在文字建议，无法与真实库存和预订链接打通，形成“规划-预订”闭环。

### 1.2 产品目标
构建一款仅限个人使用的旅行规划Agent，实现：
- 根据模糊需求推荐目的地及交通/住宿概要；
- 确定目的地后生成完整的行程表；
- 将确认后的行程转化为真实的待支付订单，并引导用户依次完成各订单支付，最终完成整段旅行的预订。

**核心原则**：所有支付操作必须由用户亲自在相应App或网页中完成，Agent绝不接触支付密码或完成最终扣款。

---

## 2. 用户与使用场景

- **用户**：产品开发者本人（单人使用）
- **使用频率**：每次旅行前使用，偶发
- **场景**：
  1. 我有出行想法，但没想好去哪里。
  2. 我确定了目的地，需要一份具体的行程方案。
  3. 我认可行程，希望直接跳转到携程/飞猪/去哪儿等平台完成支付，然后继续下一个订单。

---

## 3. 核心功能需求

### 3.1 目的地探索与票务信息初览
**用户输入**：自然语言描述的出行需求，如“清明节前后，预算4000，想去个温暖的海边，一个人，3-4天”。  
**Agent输出**：
- 推荐2-3个备选目的地，每个包含：
  - 目的地名称及推荐理由
  - 当地近期天气概况
  - 大交通预估（从用户所在城市出发的机票/火车票价格范围、耗时）
  - 中档酒店每晚估价
- 同时展示关键票务信息片段（如航班示例、车次示例），让用户对出行可行性有直观感知。

### 3.2 行程详细规划
**用户输入**：选定目的地，补充细化要求（如“选择推荐的三亚，偏好直飞，酒店要带泳池，增加一天亚龙湾行程”）。  
**Agent输出**：一份结构化的完整行程表，包括：
- **去程交通**：具体航班号/车次、起降/发到站时间、价格、中转情况
- **住宿安排**：酒店名称、地址、房型、入住/离店日期、总价
- **每日行程**：Day1至DayN的景点、餐饮建议及顺序（注明门票或活动是否需要提前预订）
- **返程交通**：同去程交通的详细信息
- **总费用预估**：交通+住宿+主要门票的合计

### 3.3 行程确认与一键预订引导
**用户输入**：对方案提出调整意见，或直接下达“就按这个来，帮我订”。  
**Agent行为**：
1. 依次为每一项需预订的服务（去程交通、酒店、返程交通等）生成对应旅行平台的预填订单或深度链接。
2. 每项预订的交互步骤：
   - Agent提示：“正在为您生成XX订单……”
   - 生成后提供链接，并告知：“请点击链接跳转至XX平台完成支付。”
   - 用户打开链接，在平台内核对信息并完成支付。
   - 用户支付成功后，需主动返回对话并输入确认指令（如“已支付”）。
   - Agent收到确认后，可调用平台的订单查询接口（若可用）进行二次验证，随后进入下一项预订。
3. 若某项预订失败（如库存售罄），Agent应提示并提供替代方案（如相近航班或酒店）。

**预订平台范围**：携程、飞猪、去哪儿（按优先级尝试）。同一类型订单应尽量在同一平台完成，减少用户跳转次数。

## 4. 交互流程示例
```text
用户：五一从北京出发，预算5000，和女朋友玩4天，要轻松浪漫。
Agent：[推荐厦门、三亚、大理] …详细描述…
用户：就三亚吧，酒店要海景房，机票不要红眼航班。
Agent：[生成完整行程，包含去程CA123、酒店三亚湾海景大床房、每日景点…]
用户：可以，帮我订。
Agent：正在为您预订去程机票 CA123 …
已生成订单链接：https://ctrip.com/xxx （请点击完成支付，完成后回复“已支付”）
用户：（点击链接，支付成功）已支付
Agent：验证支付状态…已确认。正在预订酒店……
已生成酒店订单链接：https://ctrip.com/yyy （请支付）
用户：（支付）已支付
Agent：……返程预订……全部预订完成，祝旅途愉快！
```

## 5. 技术约束与集成需求

### 5.1 后端大模型
- **模型**：豆包大模型（Doubao）
- **调用地址**：`<用户提供的API Endpoint>`
- **API Key**：`<用户提供>`
- 模型需支持长上下文对话，用于维护完整的会话状态与行程信息。

### 5.2 第三方API依赖及鉴权要求
以下为推荐接口，开发者需根据实际情况申请，并准备好对应的鉴权信息。**每一项均标注了必需的后备方案**。

| 功能模块 | 推荐 API / 服务 | 所需鉴权信息 | 后备方案（若主方案申请阻塞） |
| :--- | :--- | :--- | :--- |
| **目的地推荐与灵感** | 飞猪AI开放平台 - 目的地推荐 / 旅游灵感接口 | API Key（飞猪开放平台开发者账号） | 使用豆包大模型结合联网搜索自行生成推荐；或使用 Google Travel Explore API（需SerpApi Key） |
| **国内机票查询** | 飞猪开放平台 - 机票搜索 API | API Key | Amadeus Self-Service API（需API Key/Secret）；最后备选：构造携程/飞猪搜索结果页深度链接，仅展示链接但不提取结构化信息 |
| **国内火车票查询** | 聚合数据 - 全国火车票查询 API | API Key（聚合数据账号） | 部署开源 mcp-server-12306（仅供学习，禁止商用），或12306官方授权第三方接口（需企业资质，个人难获取） |
| **酒店查询** | 携程开放平台 - 酒店搜索 API | 合作伙伴ID/Key | 飞猪开放平台 - 酒店接口（需API Key）；Amadeus Hotel API；艺龙开放平台（需开发者账号） |
| **机票/酒店/火车票订单生成（预填）** | 途牛MCP服务 - 预订技能；或飞猪flyai技能插件 | Token/Secret（需向对应平台申请MCP服务权限） | 手动构造各平台深度链接（DeepLink），如携程的 `ctrip://` 或去哪儿 `qunar://` scheme，填入搜索参数，用户点击后手动选择并支付。此方式无需特殊鉴权，但无法预填具体订单信息。 |
| **订单状态查询** | （若上一环节使用预订API）同一服务商提供的查询接口 | 同预订接口 | 用户主动确认（“已支付”）作为唯一状态判断依据 |

**特别说明**：所有支付环节绝不涉及直接扣款API，只通过生成跳转链接让用户自主完成支付。

### 5.3 后备方案原则
- 如果高级API无法申请，应降级为**深度链接跳转+人工操作**，保证核心预订流程可走通。
- 最少可接受方案：Agent仅输出汇总行程，并附上各平台的手动搜索链接，由用户自行购买，Agent本身不介入任何订单生成。

## 6. 非功能需求

- **可用性**：单轮对话响应应在15秒内完成（若涉及外部API调用，允许超时后降级提示）。
- **可靠性**：外部API调用失败应有重试机制，并友好提示用户。
- **安全**：API Key等敏感信息必须存储在环境变量或安全配置文件，绝不能硬编码。
- **可扩展**：各功能模块（推荐、规划、预订）应解耦，方便以后替换数据源或更换大模型。
- **无登录**：系统无需用户注册/登录，所有会话数据为一次性或本地存储。

---

## 7. 数据存储需求（可选）
- 如需存储用户偏好（常住城市、出行偏好等），可使用本地轻量数据库（如SQLite）或简单JSON文件。
- 行程数据可临时存储，用于会话内持续交互，会话结束可清除。

## 8. 风险与假设

| 风险点 | 影响 | 缓解措施 |
| :--- | :--- | :--- |
| 第三方API申请困难或受限 | 无法获取结构化票务数据 | 及时启用后备方案，降级为URL生成+人工操作 |
| 豆包大模型调用不稳定 | 影响整体可用性 | 实现指数退避重试，必要时提示用户稍后重试 |
| 各旅行平台深度链接策略变动 | 生成链接失效 | 定期检查链接模板，提供手动搜索关键词作为降级 |
| 支付状态确认依赖用户主动回复 | 可能误判支付完成 | 尽量对接订单查询API做二次确认；若无API，明确提示用户仅回复“已支付”后继续，并提醒核对 |

**假设**：
- 用户已拥有主流旅行App（携程/飞猪/去哪儿）并已登录。
- 用户会在合理时间内完成支付并回复Agent。
- 所有第三方鉴权信息均已准备就绪。

## 9. 术语表

- **深度链接（DeepLink）**：一种可在App内直接跳转到特定页面的URL技术，如携程App的`ctrip://`协议。
- **MCP（Model Context Protocol）**：AI模型与外部工具交互的标准化协议，便于Agent调用API。
- **豆包大模型**：字节跳动提供的大语言模型服务。
